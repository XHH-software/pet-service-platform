## 1.3 五个亮点（简历正文，按此顺序）

> 每条都是「问题 → 手段 → 可验证结果」。加粗部分是面试官会抓的关键词。

**1. 时段防超卖：把时间拆成 30 分钟切片，用唯一索引而不是代码判断保证不撞单**

技师时间本身是区间，无法直接加约束。将其建模为 `appointment_slot`（技师 × 日期 × 时段）并按 30 分钟落行，`(staff_id, appointment_date, slot_time)` 上加唯一索引，并发冲突退化为一次 INSERT 的唯一键冲突；前置 `selectCount` 仅用于给出「该时段已被预约」的友好提示，不承担正确性。
**结果**：16 线程并发抢同一时段，仅 1 单成交、时间片只落赢家的 2 行，其余请求收到业务提示而非数据库异常。

**2. 每日限量：用「名额令牌表」替代 count-then-insert，消除 TOCTOU 窗口**

没有采用「先 count 再判断再插入」——两个请求同时 count 到 9 会一起写入第 11 单。改为建 `service_daily_quota`，`(service_item_id, quota_date, seq)` 唯一索引本身即名额，下单时按 `seq = 1..daily_limit` 逐个 INSERT，插进去即占位、全满即售罄。**判断与占位合并为同一条 SQL**，且令牌行与订单同事务，订单回滚令牌自动回收（这也是不用 Redis 计数器的原因：计数器丢 key 或回滚不减会永久多卖）。
**结果**：8 并发抢 3 个名额恰好成交 3 单；取消后名额与时间片一并释放，可再次预约。

**3. 订单超时关单：ZSet 为主 + 扫表兜底，Redis 故障不影响主链路**

下单写 Redis ZSet（score = 到期时间戳），任务每 30 秒 `ZRANGEBYSCORE` 拉取到期订单关单；另设每 5 分钟扫表兜底，覆盖 ZSet 写失败或数据丢失导致订单永久待支付的情况。两条路径调用同一个幂等方法（状态非待支付直接返回）。下单时的 ZSet 写入用 try-catch 降级为告警，**缓存故障不阻断下单**；登出黑名单同样退化为「token 自然过期」。
**结果**：测试把 Redis 指向不可用端口，先断言连接确实失败，再断言下单照常落库。

**4. 双端鉴权隔离：JWT 带端标识，两个拦截器各认一端**

管理端 `/admin/**` 与小程序 `/user/**` 共用一套 JWT，payload 携带 `type=admin|user`，两个拦截器除验签外**必须校验 type**，防止用户 token 直接调用管理端接口。`UserContext` 基于 ThreadLocal，在 `afterCompletion` 强制清理，避免 Tomcat 线程复用导致身份串号；列表接口手机号脱敏，详情接口才返回完整号码。
**结果**：用户 token 调 `/admin/**`、管理员 token 调 `/user/**` 均返回 401（5 个用例覆盖）。

**5. 并发缺陷定位与可复现的测试体系**

排查发现订单号在并发下会撞 `order_no` 唯一索引——生成器读的是已提交数据，前一事务未提交时后一事务读不到，`synchronized` 也无法解决（锁的粒度错了）。改为在写库处捕获唯一键冲突后重取号、最多重试 3 次，把数据库异常转成「下单人数较多，请稍后重试」。补 14 个集成测试：**不 mock Mapper**（要验的正是唯一索引这类约束）、H2 用 MySQL 模式、Redis 故意指向不可用端口以跑真实降级路径；配 Docker Compose 与 GitHub Actions，`mvn test` 零外部依赖可复现。

# 第二部分 · 面试拷打

## 2.0 开场：30 秒讲清项目

> 这是一个宠物洗护门店的预约系统后端，商家后台和小程序共用一套接口。业务主线是「选门店 → 选服务 → 选技师时段 → 下单 → 支付 → 到店核销 → 完成」。
> 项目里真正有难度的不是 CRUD，而是三件事：**同一技师同一时段不能被两单占用、每日服务名额不能超卖、未支付订单不能永远挂着**。我的做法都是尽量把正确性交给数据库约束，应用层只负责体验和降级。

**2 分钟主线（如果对方说"展开讲讲"）**：时间片建模 → 唯一索引兜底 → 名额令牌 → 超时双通道 → 双端隔离 → 14 个测试怎么证明。

## 2.1 架构与选型（4 问）

**Q1：为什么不用 Spring Security？**
A：这个项目只有两种身份、两个入口前缀，用两个 `HandlerInterceptor` 30 行能说清的事，上 Security 反而要读框架的过滤器链。安全需求集中在三点：验签、验端、验黑名单，拦截器完全够。如果后面要做方法级权限（`@PreAuthorize`）、多种登录方式，再引入不迟。
> 追问：拦截器能拿到方法上的注解吗？——能，`handler` 是 `HandlerMethod`，可以读方法注解做细粒度控制，这也是不上 Security 也能扩展的路径。

**Q2：为什么是单体不是微服务？**
A：单门店、单库、QPS 很低，拆开只会带来分布式事务和链路追踪的成本。项目里唯一"跨服务"的诉求是超时关单，用 Redis ZSet 就解决了，不需要为此拆一个服务。

**Q3：为什么请求体直接复用实体，不建 DTO？**
A：这是明确的取舍，不是不知道。好处是少一层转换、代码量小；代价是 `@Valid` 用不起来、入参校验散在 Service 的 if 里。这是我列在技术债第一条的问题，正确做法是按场景拆 `CreateAppointmentRequest` / `AppointmentVO` 并加分组校验——因为「创建」需要 serviceItemIds、「详情」需要携带宠物和技师名称，两者字段根本不是一套。
> 主动认账比被问出来好。

**Q4：`AppointmentService` 916 行，是不是太重了？**
A：确实偏大，但拆之前要看拆完是否更好读。它内部已经是「校验 → 组装商品 → 校验排班 → 落库占位」四段，且大量代码是 `fillList` 这类视图组装。合理的拆法是把「可约时段计算」和「视图组装」抽成独立类，`create` 主流程保留在一处——因为事务边界在这儿，拆散反而看不出资源占用与释放是否配对。

## 2.2 并发与一致性（核心区，8 问）

**Q5：你怎么保证同一时段不会被两个人同时订到？**
A：两道。第一道 `selectCount` 预检，给人话提示；第二道是 `appointment_slot` 上的唯一索引 `(staff_id, appointment_date, slot_time)`，插入时冲突就抛 `DuplicateKeyException`，我 catch 后转成业务异常。**预检负责体验，索引负责正确**——只靠预检在并发下必然击穿，只靠索引则用户只能看到「系统异常」。

> 追问：既然有了唯一索引，预检不是多余的吗？——不多余但可去掉。它唯一的价值是让 99% 的正常冲突在写库前就返回，减少一次事务开销和无谓的锁等待。如果追求极致，可以只留索引 + 异常转换。

**Q6：为什么把时间切成 30 分钟？切成 15 分钟不是更灵活？**
A：切片粒度是「灵活性」和「行数」的权衡。演示数据里最短的服务项是 20 分钟（指甲修剪），30 分钟恰好能覆盖一个短服务；15 分钟会让时间片行数翻倍，收益只是支持更碎的时段。当前 6 个技师 × 28 片（8:00–22:00）= 168 行/天，量级完全可接受。
> 追问：如果出现 45 分钟的服务怎么办？——结束时间向上取整到半小时（`ceilToHalfHour`），占用 3 片，代价是尾部有 15 分钟碎片。这是刻意的：宁可浪费一点容量，也不要出现"半片"这种无法用唯一索引表达的状态。

**Q7：每日限量为什么不用 Redis 计数器？**
A：三个理由。① 计数器丢 key 就永久多卖；② 事务回滚后 `DECR` 不一定执行，会永久少卖；③ 计数器与订单不在一个事务里，没有原子性。令牌表 `(service_item_id, quota_date, seq)` 的唯一索引本身就是名额，插入成功即占位，订单回滚时令牌行跟着回滚。
> 追问：令牌表按 `seq=1..limit` 循环插入，limit=1000 时不是要试 1000 次？——是，最坏 O(limit)。当前服务项日限 10、套餐日限 5，可以接受。量级上去的正确解法是「用聚合行 + `UPDATE ... SET used = used + 1 WHERE used < limit`」，一条语句原子占位；我用令牌表是因为它天然支持按订单回收（`appointment_id` 一删就全退），聚合行要额外维护回收逻辑。

**Q8：订单号那个 bug 具体怎么回事？**
A：`OrderNoService` 是「查当天最大号 + 1」。加了 `synchronized` 也没用——**锁只能串行化本进程的代码，串行化不了"未提交的数据不可见"**：A 事务插入了 001 但没提交，B 线程查最大号还是 000，于是也生成 001，撞唯一索引。
正确做法是在真正写库的位置捕获冲突重取号重试，而不是在生成号的位置加锁。改完最多重试 3 次，仍失败才返回「下单人数较多」。
> 追问：在事务里 catch 掉 `DuplicateKeyException` 继续执行，MySQL 允许吗？——允许。MySQL 的唯一键冲突只回滚**该条语句**，事务本身仍然有效（PostgreSQL 就不行，必须打 savepoint）。这也是我选择"重试插入"而不是"整单重来"的前提。
> 追问：重试拿到的是新号吗？——是，`next()` 每次都重新查库；因为冲突时对方已提交或已回滚，这次读到的最大值是新的。

**Q9：`booked_count` 为什么用乐观锁？直接用 `SET c = c + 1` 不行吗？**
A：**行，而且更好**。这是一处我后来复盘认为过度设计的地方：自增本身在 InnoDB 里是行锁 + 原子读改写，不存在丢失更新，用 version 重试是给自己加戏。（详见 2.7 弱项自查第 1 条）

**Q10：取消订单时你释放了哪些资源？漏一个会怎样？**
A：三类：`appointment_slot` 时间片、`service_daily_quota` 名额令牌、`schedule.booked_count` 计数。统一走 `releaseSlots()`，取消和超时关单两条路径共用。漏时间片 → 位子永远约不上；漏名额 → 当日少卖；漏计数 → 展示失真。前两个是正确性问题，第三个只是显示问题，但都会被用户当 bug 报。

**Q11：事务边界在哪？Redis 操作在事务里还是外？**
A：`create` 整个方法一个事务，写主表、明细、名额、时间片、计数全在里面，任何一步失败整体回滚。Redis 的 ZSet 写入在方法末尾、事务提交之前——严格说它在事务内，如果之后提交失败，ZSet 里会残留一个不存在的订单 id。这不致命，因为 `expireUnpaid` 是幂等的（订单不存在或状态不是待支付就直接 return），最多是一次空转。更严谨的做法是 `TransactionSynchronization#afterCommit` 里再写 ZSet，这也是我下一步想改的点。

**Q12：如果两单同时取消同一订单呢？**
A：现状是两次都读到「待支付」，都执行取消。第二次的更新是无害的（幂等写），但 `releaseSlots` 会重复执行：时间片删除第二次是 0 行，名额删除也是 0 行，`booked_count` 有 `greatest(x-1, 0)` 兜底不会变负。所以结果正确但会多一次写。严格做法是 `UPDATE ... WHERE status IN (1,2)` 判断影响行数，为 0 就直接返回——这是个 TODO，我认。

## 2.3 缓存与降级（4 问）

**Q13：Redis 挂了会怎样？逐条说。**
A：① 下单——`ZADD` 抛异常被 catch，只打 warn，订单照常落库，只是这单不会被 ZSet 关单，靠 5 分钟扫表兜底；② 支付/取消——`ZREM` 抛异常，ZSet 里留脏 id，后续 `expireUnpaid` 发现状态不符直接跳过；③ 登出——黑名单写失败，token 只能等自然过期（7 天），是安全性下降不是功能不可用；④ 读取超时订单——`catch` 后直接 return，本轮跳过，下一轮再试。**结论：功能全部可用，只有登出的即时性受损。**

**Q14：为什么扫表兜底是 5 分钟，ZSet 是 30 秒？**
A：ZSet 是正常路径，要保证体验（30 分钟未付 → 最多 30.5 分钟关闭）；扫表是异常路径，扫的是 `status=1 且 create_time < now-30min`，全表条件走 `idx_status` + `idx_create_time`，5 分钟一次对库压力可忽略。刻意把两条路径的频率拉开，避免兜底变成主路径。

**Q15：订单超时为什么用 ZSet 不用延时队列（RabbitMQ / RocketMQ）？**
A：引入 MQ 要为「一个可有可无的定时关单」多维护一个中间件，还要处理消息丢失、重复消费。ZSet 的 `ZRANGEBYSCORE` 天然按时间排序，量级在万级以内完全够。真到几十万待支付订单，再换 MQ 或时间轮。

**Q16：ZSet 里的 id 如果一直没被清掉会怎样（内存泄漏）？**
A：三个清理点：关单成功后 `ZREM`、支付/取消时 `ZREM`、拿不到锁或异常时在 `finally` 里 `ZREM`。所以只要任务在跑，集合不会无限增长。真正的风险是**任务停了**——这时 ZSet 只增不减，扫表兜底会把订单关掉但不会清 ZSet，需要一次性的对账清理。这是当前实现的盲区。

## 2.4 安全与鉴权（5 问）

**Q17：JWT 你只验签名行不行？**
A：不行。签名只能证明「这个 token 是我签的」，不能证明「它是给这个端用的」。小程序用户的 token 拿去调 `/admin/**`，只验签就放行了。所以 payload 里带 `type`，两个拦截器各自校验，`type` 不匹配直接 401。

**Q18：JWT 无状态，你怎么实现登出？**
A：写 Redis 黑名单，key 是 token 本身，TTL 设成 token 的剩余有效期（`jwtUtil.remainingSeconds`），过期自动清理。每个请求校验前先查黑名单。代价是每次请求多一次 Redis 查询，以及 Redis 挂了登出不即时——我选择退化而不是阻断，因为**登出失败比登出延迟更糟**。

**Q19：ThreadLocal 为什么一定要清？**
A：Tomcat 线程池复用线程。请求 A 把 userId 放进 ThreadLocal，处理完没清，线程被复用给请求 B，B 如果走到某条没设上下文的路径，就会读到 A 的身份——这是**越权级**的 bug，不是内存泄漏那么简单。所以放在 `afterCompletion`，无论异常与否都执行。

**Q20：密码怎么存的？手机号为什么脱敏？**
A：密码 BCrypt 加盐（`spring-security-crypto`，只用它的 `BCryptPasswordEncoder`，不引入整个 Security）。手机号在列表接口脱敏成 `138****1234`，只有详情接口返回完整号码——因为列表可能被截图、被批量爬，详情是单条有明确使用场景。

**Q21：`app.wx.mock=true` 有什么风险？**
A：开发期为了方便，任意 code 都能登成 1 号客户。叠加 `application.yml` 里带默认值的 JWT secret，**如果原样部署到公网，等于没有鉴权**。这是我在 README 里明确标注的边界：生产必须用环境变量覆盖 `JWT_SECRET`、配置真实 `app-id/app-secret` 并关闭 mock。

## 2.5 数据模型与 SQL（5 问）

**Q22：为什么不用物理外键？**
A：两个原因：① 外键在写入时会加额外的锁，高并发插入容易死锁；② 分库分表后外键必然要拆。我改用「应用层校验 + 索引」，代价是删除时可能留下孤儿数据——这是我列在技术债里的问题，正确做法是在删除服务项目/技师时显式检查引用。

**Q23：日历/可约时段接口怎么查的？会不会慢？**
A：先查该技师当天排班是否启用，再拿已占用的 `slot_time` 集合，用 `isFree()` 按 30 分钟逐片判断是否落在已占区间内，最后过滤掉已过去的时段。一次查询拿到当天所有占用片，内存里判断，不会 N+1。
> 追问：为什么不在 SQL 里做区间判断？——可以，但可约时段还要和「服务时长、宠物体型、当日名额」一起算，放内存里逻辑更清楚；数据量是「一天几十片」，内存判断成本可忽略。

**Q24：哪些字段建了索引，为什么？**
A：`appointment` 上 `(appointment_date, staff_id)` 支撑日历和后台按日筛选，`customer_id` 支撑「我的订单」，`status` 和 `create_time` 支撑扫表兜底；`appointment_slot` 的唯一索引同时充当查询索引（技师 + 日期前缀）；`service_daily_quota` 的 `appointment_id` 用于按单回收。

**Q25：金额用什么类型？**
A：`DECIMAL(10,2)`，Java 侧 `BigDecimal`。不用 double 是常识，但要注意 Jackson 序列化 `BigDecimal` 默认可能输出科学计数法或丢精度，项目里统一了 Jackson 的时区和属性包含策略。金额在写入时做「价格快照」——`appointment_item` 存下单时的单价，服务项目后来调价不影响历史订单。

**Q26：如果要做多门店，你的表要怎么改？**
A：`staff`、`schedule`、`service_item`、`appointment` 都要加 `shop_id`，且唯一索引要带上它——`(shop_id, staff_id, date, slot_time)`（严格说 staff_id 已隐含门店，但加 `shop_id` 前缀能让按店查询走同一索引）。JWT 里要带 `shopId` 或角色，拦截器按门店过滤。这是当前项目最大的一块缺失，`shop` 表只有一条记录。

## 2.6 测试与工程化（4 问）

**Q27：这 14 个测试到底证明了什么？**
A：四个命题。① 并发抢同一时段只有 1 单成功且计数只 +1；② 8 并发抢 3 个名额恰好成交 3 单；③ 双端 token 交叉调用返回 401；④ Redis 连不上时下单仍成功。
每个命题都对应一个我声称的设计，**测试的作用是把"我说的"变成"可执行的"**。

**Q28：为什么用 H2 不用 Testcontainers？**
A：为了让 `mvn test` 零依赖可复现——面试官或任何人 clone 下来就能跑，不需要 Docker 和 MySQL。代价是 H2 与 MySQL 有方言和隔离级别差异，我用 `MODE=MySQL` + `LOCK_TIMEOUT=15000` 对齐了本题用到的语义。
> 追问：这个取舍有没有掩盖问题？——有，2.7 第 1 条就是被掩盖的那个。（诚实回答，反而加分）

**Q29：为什么不用 Mockito mock Mapper？**
A：因为被测对象就是「唯一索引在并发下会不会拦住第二单」，mock 掉 Mapper 等于把被测对象删了，测试只会证明「我的 mock 写对了」。这类测试必须用真库。

**Q30：CI 里跑什么？为什么不会红？**
A：JDK 11 + `mvn test`，不启 MySQL 和 Redis（测试用 H2，Redis 指向不可用端口本来就是被测场景），所以不需要 service 容器，构建稳定。`mvn package` 会产出可执行 jar，Dockerfile 多阶段构建，compose 里 MySQL healthcheck 通过后才启动应用。

## 2.7 弱项自查（主动暴露，比被问出来强）

**1. `changeBooked` 的乐观锁重试在 MySQL 默认 RR 下是空转**

`changeBooked` 每次重试都 `selectById` 拿 version。但在 `REPEATABLE READ` 下，同一事务内的一致性读共用第一次 SELECT 建立的快照，**重试读到的还是旧 version**，5 次必然全失败，最后只打一条 warn。
H2 默认是 `READ_COMMITTED`，所以测试里能过——这正好说明「测试环境与生产隔离级别不一致」会掩盖问题。

**正确答法**：`UPDATE schedule SET booked_count = booked_count + 1 WHERE id = ?` 本身就是原子的（行锁 + 读改写），根本不需要 version；version 只该用在「读出来算一下再写回去」的场景。这条我准备改成原子自增并删掉重试循环。
**影响面**：`booked_count` 只用于排班周视图展示，不参与可约判断（可约判断看 `appointment_slot`），所以是展示失真，不是超卖。

**2. 取消的并发幂等**：见 Q12，结果正确但会重复写，应该用 `WHERE status IN (1,2)` 判影响行数。

**3. ZSet 写入在事务内**：见 Q11，应挪到 `afterCommit`。

**4. 默认配置不安全**：`WX_MOCK=true` + 带默认值的 JWT secret，演示方便、上生产是洞。

**5. 无压测数据**：所有并发结论都是「正确性」层面的，没有「容量」层面的数字。被问吞吐就直接说没做过压测，不要编。

> 这五条我建议在面试里主动挑 1~2 条说（尤其是第 1 条），因为它证明你会复盘自己的代码，而不是只会复述设计。
